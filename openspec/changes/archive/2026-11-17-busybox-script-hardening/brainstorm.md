## Design Summary

Issue #220. The BusyBox/SysV init script generated by `service install` runs as root on non-systemd Linux hosts. Two defects make it unsafe:

1. **Shell injection.** Binary, config and state paths are interpolated verbatim inside double quotes (`DAEMON="{binary}"`, `CONFIG="{config}"`, `export IROH_TUNNEL_STATE_DIR="{state}"`). A legal path containing `$(...)`, backticks, `$name`, `"` or `\` is expanded by the shell when root runs the script. Config paths can come from a user-owned directory (system install with a user config, SM-04), so an unprivileged user can get code executed as root.
2. **PID reuse.** `start`, `stop` and `status` trust any live `kill -0 $(cat $PIDFILE)`. After a crash or reboot the recorded PID can belong to an unrelated process: `start` then refuses to start the daemon, `status` reports it running, and `stop` sends SIGTERM/SIGKILL to the unrelated process.

The validated design:

- Every value interpolated into the script is serialized as a POSIX single-quoted literal using the host's existing `shell_quote`. Paths are not refused; any legal path works and reaches the daemon unchanged.
- The script records, next to the PID, the daemon executable it launched. A PID counts as "ours" only when the process's `/proc/<pid>/exe` matches that recorded executable (also accepting the kernel's ` (deleted)` suffix, which appears after a managed copy is replaced on re-install). Otherwise the PID file is stale: it is removed, `stop` signals nothing, `status` reports not running, and `start` launches the daemon.
- PID files written by older scripts (PID only) get a narrow compatibility check so that re-installing over a running legacy registration still stops the old daemon, even when the re-install changes the binary path (for example user binary → managed copy from #215).
- The effective-binary reader (`DAEMON` of the init script, used by CLI `start`/`restart` binary trust) reads both the new single-quoted form and the legacy double-quoted form.

Existing requirements touched:

- `system-service-management` → "BusyBox init script content and lifecycle": **altered**. The stop policy (SIGTERM, then SIGKILL after 5 s) and paths are kept; the requirement gains literal quoting and process-identity checks for start/stop/status.
- `unix-service-binary-trust` → "CLI start and restart re-check the registered binary", scenario "Effective definition per backend": unchanged in meaning (`DAEMON` of the init script), but must hold for both script generations.
- `system-service-management` → "BusyBox backend needs root and ignores user scope": unchanged.

## Alternatives Considered

### Alternative A: Refuse paths with shell metacharacters at install time
- **Approach**: Validate binary/config/state paths and fail closed with a clear message when they contain characters the double-quoted template cannot hold.
- **Pros**: Tiny change to the template; parser unchanged.
- **Cons**: Rejects legal paths (spaces with `$`, quotes); the safety rests on a denylist being complete; legacy scripts already on disk stay as they are.
- **Why not chosen**: Quoting is total (every string is representable) and reuses an existing, tested helper; refusal would be a user-visible restriction for no gain.

### Alternative B: Confirm identity through the role ownership lock (`<binary> <role> status --json`)
- **Approach**: Before signalling, ask the daemon binary whether the role's lock is held and by which PID.
- **Pros**: Robust to binary path changes; reuses the authoritative liveness source.
- **Cons**: `status --json` returns the raw snapshot (snapshot PID, not lock owner PID), so a public CLI contract would have to change; depends on the new binary reading the old binary's lock; runs the daemon binary on every init verb.
- **Why not chosen**: Larger blast radius (public CLI change) than a pure-shell check that works on the leanest BusyBox.

### Alternative C: Compare `/proc/<pid>/exe` with the current `$DAEMON` only
- **Approach**: No recorded executable; compare the live process with whatever the current script names.
- **Pros**: Simplest script.
- **Cons**: A re-install that changes the binary path leaves the old daemon running; the new daemon is refused by the ownership lock, so the service stays on the old binary until reboot or a manual kill.
- **Why not chosen**: Breaks the upgrade path from #215 (user binary → managed copy).

### Legacy PID file alternatives (sub-decision)
- **Strict only** (compare with new `$DAEMON`): simplest, but the same upgrade breakage as Alternative C; would need a documented manual stop.
- **Install stops with the old script before writing the new one**: runs the PID-reuse-prone logic one last time and changes the install flow.
- **Chosen: narrow compatibility check** for PID-only files (see Key Decisions).

## Agreed Approach

Single-quote every interpolated value with the shared host `shell_quote`, and make the script verify process identity through `/proc/<pid>/exe` against the executable recorded at start (Alternative "record + verify"), with a narrow fallback for legacy PID-only files. Chosen because it closes both defects in the script itself, needs no public CLI change, works on a minimal BusyBox, and keeps re-install over existing registrations working, including binary path changes.

## Key Decisions

- Quote, don't refuse: any legal path is accepted and reaches the daemon as the literal path.
- Reuse the existing host `shell_quote`; do not merge it with the CLI's copy in `src/render.rs` (that is #225's scope).
- Identity = recorded launched executable vs `/proc/<pid>/exe`, accepting the ` (deleted)` suffix.
- A PID that fails the identity check is stale: removed, never signalled, reported not running, does not block `start`.
- Legacy PID-only files: treated as ours when `/proc/<pid>/exe` matches the current `$DAEMON`, or when the executable's basename starts with `iroh-tunnel` and its command line carries this role's `run --config <config>`. New-format PID files always use the strict check.
- Re-install keeps rewriting the script and running `restart`, which is how existing registrations migrate to the hardened script.
- The effective-binary reader accepts both script generations.
- Acceptance tests execute a rendered script with `/bin/sh` (not string asserts), using a fake daemon and an injected path, a stale PID pointing at an unrelated live process, and a legacy PID file.

## Open Questions

- None blocking. Making `/proc` checks testable on macOS (no `/proc`) is left to design: the test harness may need a seam for the proc root, and Linux-only execution tests may be gated by `cfg`.
