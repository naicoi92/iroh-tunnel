00 / System context · confirmed contract

Two peers, one encrypted tunnel

Each peer owns its endpoint identity, role configuration and status. Address lookup and relay assist connectivity; a direct path may replace relay. This is a target view, not a current implementation claim.

01 / Architecture

Roles share a domain, not a runtime dependency

Three independent executables compose the same modules. Dependency direction is a design proposal; exact crate boundaries remain open.

Infrastructure adapters depend inward on application-facing ports; exact port and crate boundaries are proposed and remain open.

Architecture / Component dependencies · proposed

Composition and dependency boundaries

Arrows show source dependencies, not network traffic. The three entrypoints are independently runnable; exact crate boundaries and port interfaces remain open.

Domain has no dependency on Iroh, the filesystem, or OS service APIs. Adapters point inward to application-facing ports; runtime wiring is performed by each entrypoint. The diagram does not prescribe crate names or UDP transport.

02 / Deployment

One role per host, or one binary for both

Images and packages are independently distributed. Versions may differ when their tunnel protocols are compatible.

Installer defaults to system-wide and installs all three. A non-elevated installer chooses user or system service scope; effective root or an elevated Administrator defaults to system. macOS uses LaunchAgent or LaunchDaemon; the Windows user background mechanism remains open. Images: all-in-one, serve, access.

03 / Sequence

TCP: one connection, many channels

Multiplex is always enabled. A protocol mismatch fails clearly; no silent downgrade.

04 / Sequence

UDP: preserve datagrams and client identity

Transport, fragmentation, maximum payload and resource limits are not decided. Benchmark Iroh 1.4.1 on direct and relay paths before selecting them.

Best effort: packets can be lost, duplicated or reordered. The logical flow is an application concept, not a TCP connection; idle flow cleanup and resource limits require detailed design.

05 / Command and background execution

Separate quick execution from configured operation

Conceptual flow; exact flags and Windows user-scope mechanism remain implementation decisions.

Windows system scope uses SCM; regular-user execution must run in the login session, but its mechanism is not yet chosen. Non-elevated users choose user or system scope. Selecting system or passing --system without permission stops with instructions to rerun using sudo on Unix or an elevated Administrator terminal on Windows; no automatic elevation or fallback. Effective root or an elevated Administrator defaults to system scope without a scope prompt.

06 / Flowchart

Install and update with an explicit trust gate

The installer installs all three by default; each executable self-updates independently. Package-managed installs delegate to the corresponding package manager; container deployments replace the image.

A signature-verification bypass is an explicit choice before installation, never an automatic fallback; it emits a security warning and weakens provenance guarantees. Checksum-bypass policy remains to be specified. NodeId is public identity, not authorization; exposed services need their own access controls.

07 / Architecture · config and state

Separate user data from execution scope

Arrows indicate shared storage access, not network traffic. CLI manages config and reads status; configured runs and services read config and write status. Services pin their installing user's absolute paths.

macOS / Linux default to ~/.config/iroh-tunnel and ~/.local/state/iroh-tunnel; Windows uses LocalAppData. Legacy macOS config is copied only if the new file is absent; copy failures do not generate a replacement identity. Exact locking and legacy paths remain open.

08 / Architecture · service control

Service installation crosses a privilege boundary

These arrows show the installation decision; runtime tunnel traffic is separate.

Horizontal path: sufficient privileges. Downward path: insufficient privileges. Non-elevated users choose scope; root or elevated Administrator defaults to system. No automatic elevation or fallback. Confirm replacement of a service targeting another user's config. Windows user login-background mechanism remains undecided. A privileged system service reading user-editable config crosses a trust boundary: account, ownership, file integrity and symlink checks require security design before implementation; absolute paths alone are insufficient.

09 / Architecture · distribution

Three independently managed artifacts

Arrows show packaging and delivery, not runtime process dependencies.

Each executable updates independently. A package manager owns its package; containers are replaced rather than self-updated. Trust rotation, rollback and exact platform build matrix remain open.

10 / Architecture · trust

Encrypted tunnel is not service authorization

Trust boundaries and security responsibilities; no new authentication service is implied.

Relay carries encrypted traffic. Knowing NodeId and service name is not an authorization mechanism. Bypassing verification is explicit; checksum-bypass semantics remain unspecified.

11 / Runtime · ownership

Listeners share connections, not client state

Conceptual target; retry and shutdown policy remain proposed. Arrows indicate ownership or use, not a wire protocol.

Serve routes traffic to the fixed configured service. TCP uses one stream per client; the role runtime owns UDP flow mappings, and uses transport connections to carry them. UDP transport and payload limits await benchmark. Reconnect, shutdown and resource limits require detailed design.

12 / Platform architecture

Service lifecycle adapters by platform

These are platform integration targets. They do not introduce new network services.

13 / Identity and config lifecycle

Preserve identity through migration

Configured-run path uses the new config if present; only otherwise checks the legacy location. Quick run is independent.

Both quick and configured execution acquire ownership before running; a conflict refuses the second instance. If legacy copy fails, stop with an actionable error; do not create a replacement identity. Locking and exact legacy paths remain to be designed.
